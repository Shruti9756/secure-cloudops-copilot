# SecureCloudOps Copilot — V0.3 Release Checklist

> Release goal: a locally verified, reliable, and measurable RAG baseline that improves evidence retrieval using reproducible evaluation while making document processing retryable, idempotent, observable, and safe across workspaces.

## What V0.3 means

V0.3 builds on the released V0.2 multi-tenant security baseline. It keeps Cognito authentication, PostgreSQL-backed membership and role authorization, organization-scoped retrieval, safe auditing, and document visibility controls while improving RAG quality and ingestion reliability.

The release uses a reviewed synthetic corpus to compare semantic, lexical, hybrid, and reranked retrieval. It integrates hybrid semantic and BM25 retrieval only after measuring the quality, latency, and token tradeoffs. It also moves document processing beyond a simple polling baseline by adding persisted retry state, Redis locks and progress, authorized retry, embedding caching, layered limits, quotas, and response-cache invalidation.

This remains a local-development learning baseline, not a production deployment. It does not claim production-scale latency, Amazon SQS durability, a dead-letter queue, managed Redis, database row-level security, or complete model-judged evaluation.

## Completed ingestion reliability capabilities

- [x] Document processing runs in a separate Docker Compose worker rather than inside the upload request.
- [x] Source checksums prevent unchanged documents from creating duplicate processing work.
- [x] Persisted processing-attempt count, next-attempt timestamp, and safe failure reason support retry state.
- [x] Retry delay uses bounded exponential backoff and stops after a configured maximum number of attempts.
- [x] Failed documents can be retried only through an authorized API operation and role-aware browser control.
- [x] Redis document locks prevent two workers from processing the same document concurrently.
- [x] Ownership-safe lock release prevents one worker from deleting another worker's lock.
- [x] Lock heartbeats renew ownership while long embedding calls are running.
- [x] Redis records short-lived processing stages without storing document content.
- [x] Document status responses combine persistent PostgreSQL state with short-lived Redis progress.
- [x] Normalized-text embedding caching avoids repeated provider work for identical chunk text.
- [x] Workspace knowledge revisions invalidate cached answers after document changes.

## Completed usage and resilience controls

- [x] Ask requests enforce layered per-user and per-organization request limits.
- [x] Ask requests enforce per-organization model-token quotas.
- [x] Rate-limit and quota decisions are represented in safe audit metadata.
- [x] Redis unavailability does not bypass authorization.
- [x] Processing failures roll back incomplete document changes before retry state is committed.
- [x] Worker logs contain operational identifiers and counts rather than document content, questions, answers, embeddings, credentials, or tokens.

## Completed RAG-quality capabilities

- [x] Versioned 50-question synthetic retrieval catalogue with reviewed expected document and chunk identifiers.
- [x] Transparent Precision@k and Recall@k calculations.
- [x] Semantic retrieval through pgvector cosine distance.
- [x] Custom BM25 lexical retrieval without an additional third-party ranking dependency.
- [x] Reciprocal-rank fusion of semantic and lexical candidates.
- [x] Identifier-aware reranking evaluated after the baseline was recorded.
- [x] Hybrid retrieval integrated into the production RAG service.
- [x] Semantic anchoring prevents lexical-only matches from producing unsupported answers.
- [x] Eight-case answer evaluation covers grounded answers, citations, and required abstentions.
- [x] Controlled comparison of `1200/200` and `600/100` chunking profiles.
- [x] Optional Ragas evaluation explicitly deferred while transparent custom metrics remain the primary release evidence.

## Recorded V0.3 evaluation results

- [x] At retrieval limit three, semantic retrieval recorded mean Precision@3 `0.300` and Recall@3 `0.880`.
- [x] At retrieval limit three, hybrid retrieval recorded mean Precision@3 `0.333` and Recall@3 `0.980`.
- [x] Hybrid retrieval therefore improved Recall@3 by `0.100` on the controlled 50-question corpus.
- [x] Hybrid-reranked retrieval improved top-one ordering but did not improve the top-three evidence set over ordinary hybrid retrieval.
- [x] The production path uses hybrid retrieval without the additional reranking stage.
- [x] Post-hybrid answer evaluation retained `1.000` outcome accuracy, citation correctness, abstention correctness, and overall pass rate.
- [x] The current `1200/200` chunking profile was retained because `600/100` reduced Recall@3, created more chunks, used more embedding tokens, and increased measured latency.
- [x] The chunking comparison always rolls back its temporary organizations, workspaces, documents, chunks, and embeddings.
- [x] The consolidated report documents quality, latency, token, cost-proxy, and scope limitations.
