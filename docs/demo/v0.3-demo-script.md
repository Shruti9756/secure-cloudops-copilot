# SecureCloudOps Copilot — V0.3 Demo Script

> Status: release-candidate walkthrough for V0.3.
>
> Target duration: 5–6 minutes.
>
> Use synthetic demonstration data only. Never show a password, JWT, AWS credential, `.env` value, Cognito authorization code, Redis secret, or presigned S3 URL.

## Purpose

Use this walkthrough to explain how V0.3 turns the V0.2 secure multi-tenant RAG baseline into a more reliable and measurable system.

The story has two connected parts:

1. document processing is safer to retry and easier to observe; and
2. the retrieval decision is supported by reproducible measurements rather than intuition.

## 1. Introduce the V0.3 problem

Say:

> V0.2 proved authenticated, organization-scoped RAG. V0.3 asks two new questions: can document processing recover safely from failures, and can we prove that a retrieval change improves evidence quality without weakening citations or abstention?

Show the V0.3 section of `VERSIONED_ROADMAP.md` and the consolidated evaluation report.

Explain that V0.3 is still a local-development baseline. It does not claim a managed cloud queue, production-scale load testing, or complete model-judged evaluation.

## 2. Show reliable document processing

Upload a small synthetic Markdown document from an authorized administrator or manager account.

Show the document status changing through the available processing stages until it reaches `embedded` and displays **Processing complete**.

Explain:

> The upload request stores validated, redacted document state. A separate worker claims the job, holds a Redis lock, chunks the document, reuses cached embeddings when possible, and records short-lived progress. PostgreSQL remains the durable source of truth; Redis stores coordination and temporary status.

Point out these concepts:

- **Idempotency:** uploading unchanged content does not create duplicate embedding work.
- **Distributed lock:** two workers cannot safely process the same document at the same time.
- **Lock heartbeat:** a worker renews its ownership while a long embedding call is running.
- **Progress state:** the UI can show the current stage without writing every short-lived update to PostgreSQL.
- **Retry state:** a transient provider failure schedules bounded exponential retry; repeated failures eventually stop rather than retrying forever.

Do not intentionally damage live data for the demo. Use the automated tests and release checklist as evidence for failure and retry paths when a safe synthetic failure is not already available.

## 3. Explain hybrid retrieval

Show the retrieval flow:

```text
Question
   ├── semantic search: meaning and conceptual similarity
   └── BM25 search: exact words, versions, and incident identifiers
                     ↓
             reciprocal-rank fusion
                     ↓
           top three authorized chunks
                     ↓
       cited answer or safe abstention
```

Say:

> Semantic retrieval is useful when the question and document use different wording. BM25 is strong for exact identifiers such as versions and incident IDs. Reciprocal-rank fusion combines their rankings without pretending their raw scores use the same scale.

Explain that retrieval still applies organization, workspace, role, and document-visibility filters before evidence is supplied to the model.

## 4. Show the measured retrieval improvement

Open `docs/evaluation/v0.3-evaluation-report.md` and show the limit-three comparison.

Highlight:

| Strategy | Precision@3 | Recall@3 |
|---|---:|---:|
| Semantic | 0.300 | 0.880 |
| Hybrid | 0.333 | 0.980 |

Say:

> On 50 reviewed synthetic questions, hybrid retrieval increased mean Recall@3 from 0.880 to 0.980. Recall measures how much of the expected evidence appeared in the returned set. Precision also increased from 0.300 to 0.333.

Explain why hybrid reranking was not selected as the production default:

> Reranking produced the strongest first result, but the application uses three evidence chunks. At three chunks it did not improve quality over ordinary hybrid retrieval and added measured latency, so V0.3 keeps the simpler hybrid path.

State that the latency values came from one local machine and are not production guarantees.

## 5. Show answer-quality preservation

Run or show the recorded output from:

```powershell
cd services\api
uv run python -m scripts.evaluate_answers
```

Highlight:

- outcome accuracy: `1.000`;
- citation correctness: `1.000`;
- abstention correctness: `1.000`; and
- overall pass rate: `1.000`.

Say:

> Better retrieval is useful only if the final answer remains safe. Four cases required grounded cited answers, and four required the system to admit that it lacked evidence. All eight passed after hybrid retrieval was integrated.

Clarify that eight synthetic cases are regression evidence, not proof of universal correctness.

## 6. Show the chunking decision

Run or show the recorded output from:

```powershell
uv run python -m scripts.evaluate_chunking
```

Explain the two profiles:

- current: `1200` characters with `200` overlap;
- smaller: `600` characters with `100` overlap.

Show that the smaller profile:

- created 12 chunks instead of 7;
- used 1511 document-embedding tokens instead of 1413;
- reduced Recall@3 from `0.980` to `0.940`;
- increased measured mean and P95 retrieval latency; and
- improved Precision@3 by only `0.007`.

Say:

> The experiment justified keeping the current chunking profile. An evidence-backed decision can correctly be a decision not to change the configuration.

Point out that the comparison uses temporary UUID-scoped workspaces inside one database transaction and always rolls the transaction back.

## 7. Explain limits, quotas, and caching

Summarize:

- user and organization request limits prevent one actor or organization from consuming the whole request budget;
- organization token quotas bound local model usage over a fixed window;
- embedding caching avoids recomputing identical normalized text;
- workspace knowledge revisions invalidate answer caches after the indexed knowledge changes; and
- audit events record safe decision metadata without storing raw questions or answers.

Say:

> These controls make resource usage more predictable, but local Ollama token counts are compute proxies rather than billed cloud costs.

## 8. Explain the Ragas decision

Say:

> V0.3 uses transparent deterministic metrics as its primary evidence. Ragas was considered as an optional second framework but deferred because judge-model scores can be stochastic and add another model and cost variable. A future Ragas experiment must be reported separately rather than mixed into deterministic results.

This is a scope decision, not a claim that custom metrics replace every possible evaluation method.

## 9. Close with verification

Show the V0.3 release checklist and summarize:

- the default API suite passes with 459 tests and one live test deselected;
- the 50-question retrieval benchmark records the hybrid quality improvement;
- the eight-case answer benchmark passes after hybrid integration;
- the chunking experiment records why `1200/200` remains the default;
- frontend, MCP server, Compose, clean-clone, and GitHub checks are release gates; and
- all evidence uses synthetic data.

Finish with:

> V0.3 does not claim that this local system is production-ready. It demonstrates a stronger engineering process: reliability controls are tested, retrieval changes are measured, tradeoffs are documented, and unsupported questions still fail safely. V0.4 will move the proven design toward an AWS cloud platform.
