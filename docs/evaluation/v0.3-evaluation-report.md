# SecureCloudOps Copilot V0.3 Evaluation Report

## Decision summary

V0.3 adopts hybrid semantic and BM25 retrieval with reciprocal-rank fusion for the production RAG path.

On the controlled 50-question benchmark at the application's retrieval limit of three:

- semantic retrieval achieved `0.880` mean Recall@3;
- hybrid retrieval achieved `0.980` mean Recall@3;
- the absolute Recall@3 improvement was `0.100`;
- the eight-case answer evaluation retained `1.000` outcome accuracy, citation correctness, abstention correctness, and overall pass rate after hybrid integration.

The current `1200` character chunk size with `200` characters of overlap is retained. The evaluated `600/100` profile created more chunks, used more document-embedding tokens, reduced Recall@3, and increased measured latency.

These results describe a synthetic controlled corpus on one local-development machine. They are not production performance guarantees.

## Evaluation scope

The benchmark used:

- 50 reviewed retrieval questions;
- eight reviewed answer-quality cases;
- five version-controlled synthetic documents under `docs/demo-data`;
- seven chunks for the current chunking profile;
- `mxbai-embed-large` for embeddings;
- `qwen3:4b-instruct` for answer generation;
- PostgreSQL with pgvector;
- custom BM25 lexical retrieval;
- reciprocal-rank fusion for hybrid retrieval.

All evaluation data is synthetic. No production documents, credentials, customer information, or real incident data was used.

## Retrieval comparison

### Retrieval limit 1

| Strategy | Mean Precision@1 | Mean Recall@1 | Relevant first result |
|---|---:|---:|---:|
| Semantic | 0.620 | 0.610 | 31 of 50 |
| Lexical BM25 | 0.780 | 0.780 | 39 of 50 |
| Hybrid | 0.720 | 0.710 | 36 of 50 |
| Hybrid reranked | 0.820 | 0.810 | 41 of 50 |

The identifier-aware reranker produced the strongest first result. It returned a relevant first chunk for 41 questions, compared with 31 for semantic retrieval.

The production RAG path uses three evidence chunks, so the limit-three results are more important for the application decision.

### Retrieval limit 3

| Strategy | Mean Precision@3 | Mean Recall@3 | Query embedding tokens |
|---|---:|---:|---:|
| Semantic | 0.300 | 0.880 | 846 |
| Lexical BM25 | 0.327 | 0.960 | 0 |
| Hybrid | 0.333 | 0.980 | 846 |
| Hybrid reranked | 0.333 | 0.980 | 846 |

Hybrid retrieval improved mean Recall@3 by `0.100` over semantic retrieval while also increasing mean Precision@3 from `0.300` to `0.333`.

Reranking did not improve the top-three evidence set beyond ordinary hybrid retrieval. Therefore, the production RAG path uses hybrid retrieval without the additional reranking step.

## Retrieval latency

The following values came from one sequential local run after warming the embedding model:

| Strategy | Mean latency | P50 latency | P95 latency |
|---|---:|---:|---:|
| Semantic | 1443.685 ms | 843.724 ms | 3659.028 ms |
| Lexical BM25 | 6.063 ms | 4.435 ms | 8.281 ms |
| Hybrid | 1090.124 ms | 533.928 ms | 3316.066 ms |
| Hybrid reranked | 1615.664 ms | 1385.279 ms | 4303.762 ms |

Lexical retrieval was much faster because it did not create a query embedding.

Hybrid, semantic, and hybrid-reranked retrieval each used 846 query-embedding input tokens. These token counts measure local model work and are not billed monetary costs.

The recorded hybrid latency was lower than semantic latency during this run, but the experiment was not repeated enough to claim a general latency improvement. The quality improvement, not the single-run latency difference, justifies adopting hybrid retrieval.

The reranked strategy had the highest measured mean and tail latency at limit three without improving Recall@3, so it remains an evaluation result rather than the production default.

## Answer-quality validation

The post-integration answer evaluation contained:

- four questions requiring grounded answers;
- four questions requiring safe insufficient-evidence responses.

| Metric | Semantic baseline | Hybrid production path | Change |
|---|---:|---:|---:|
| Outcome accuracy | 1.000 | 1.000 | 0.000 |
| Citation correctness | 1.000 | 1.000 | 0.000 |
| Abstention correctness | 1.000 | 1.000 | 0.000 |
| Overall pass rate | 1.000 | 1.000 | 0.000 |

Hybrid retrieval preserved all measured answer-quality results.

Token counts changed as follows:

| Token category | Semantic baseline | Hybrid run | Difference |
|---|---:|---:|---:|
| Query embedding input | 124 | 124 | 0 |
| Generation prompt | 4278 | 4824 | +546 |
| Generation completion | 168 | 182 | +14 |

The larger prompt count reflects the evidence supplied during this particular hybrid run. It is a measured tradeoff, not proof that every hybrid request will use exactly 546 additional prompt tokens.

## Chunking comparison

| Profile | Chunks | Embedding tokens | Precision@3 | Recall@3 | Mean latency | P95 latency |
|---|---:|---:|---:|---:|---:|---:|
| Current `1200/200` | 7 | 1413 | 0.333 | 0.980 | 2966.677 ms | 3361.856 ms |
| Smaller `600/100` | 12 | 1511 | 0.340 | 0.940 | 3068.756 ms | 3847.958 ms |

Compared with the current profile, the smaller profile:

- improved Precision@3 by only `0.007`;
- reduced Recall@3 by `0.040`;
- created five additional chunks, an increase of `71.429%`;
- used 98 additional document-embedding tokens, an increase of `6.936%`;
- increased measured mean latency by `102.079 ms`;
- increased measured P95 latency by `486.102 ms`.

The current `1200/200` profile remains the production default.

The comparison created temporary UUID-scoped organizations and workspaces inside a PostgreSQL transaction. The transaction was always rolled back, including on failure. A database query after the live evaluation confirmed that no `chunk-eval-*` workspaces remained.

## Reliability and cost controls

V0.3 also added:

- background document processing outside the upload request;
- checksum-based idempotency;
- bounded exponential retry;
- persisted failure reasons and processing-attempt state;
- authorized retry from the browser;
- Redis distributed document locks;
- lock renewal during long embedding operations;
- short-lived Redis job progress;
- per-user and per-organization request limits;
- per-organization model-token quotas;
- normalized-text embedding caching;
- workspace knowledge revisions for response-cache invalidation.

These controls improve local reliability, but they are not a substitute for a durable cloud queue. Amazon SQS and a dead-letter queue remain future cloud-platform work.

## Optional Ragas evaluation

Ragas was considered as an optional second evaluation framework but was deferred from V0.3.

The release keeps transparent deterministic metrics as its primary evidence:

- Precision@k;
- Recall@k;
- citation correctness;
- abstention correctness;
- answer outcome accuracy;
- latency percentiles;
- embedding and generation token counts.

A future Ragas experiment may add model-judged faithfulness and context-relevance measurements. Such measurements must be recorded separately because judge-model results can be stochastic and may introduce additional model cost.

## Limitations

- The corpus contains only five synthetic documents.
- Retrieval labels cover 50 synthetic questions.
- Answer evaluation covers eight synthetic cases.
- Latency came from one local machine and is not a load test.
- Local Ollama token counts are compute-usage proxies, not billed AWS costs.
- Perfect controlled-corpus answer results do not prove correctness for unseen organizations or documents.
- The local database-backed worker is not a managed durable message queue.
- Ragas and broader judge-model evaluation remain optional future work.

## Conclusion

V0.3 provides reproducible evidence for its production retrieval decision.

Hybrid retrieval improves evidence coverage at the application's top-three retrieval limit, preserves the controlled answer-quality results, and avoids the additional latency of the evaluated reranking stage. The current chunking profile also remains preferable based on measured recall, chunk count, embedding work, and latency.
